What is this Data Structure Visualizer?

    
This is a free, browser-based tool for visualizing and debugging data structures written in Python. Unlike most visualizers, which only animate a fixed, pre-built algorithm, this tool runs your own code — paste any Python implementation of a binary search tree, an n-ary tree, a linked list, a graph, a heap, a stack, or a queue, along with driver code that exercises it, and it executes the real Python interpreter in your browser to trace exactly what your code does, line by line.

  

  

    
How it works

    
The tool uses Pyodide, a full CPython runtime compiled to WebAssembly, so your code runs as real Python — not a simulation or reimplementation. As execution proceeds, a line-level tracer inspects every live object reachable from your code after each statement and walks its actual attributes and container contents generically — whatever they're called — to build the real reference graph your code has constructed. It then classifies that graph purely from its shape: how many parents each node has, whether there's a cycle, whether every node branches to at most one further node. No attribute name, class name, or variable name is ever pattern-matched. The result is a step-by-step debugger that shows the actual line executing, the live local variables in the current stack frame, the structure redrawn at every step, and the real traversal path highlighted as it moves through the structure.

  

  

    
Supported data structures

    
Nothing here is keyed off what you name anything — these are pure descriptions of shape, discovered from the live object graph itself:

    
    
      
  • Trees — any acyclic structure where every node (other than the root) is reached from exactly one other node, however many children it has and whatever its child attributes/lists are called. Binary and n-ary trees both fall out of the same rule.
    • 
      
  • Linked lists — a chain where every node connects to at most one further node; open or circular, singly or doubly (a doubly-linked back-reference is detected as two objects pointing at each other, not by an attribute named prev).
    • 
      
  • Graphs — anything with a real cycle or a node reachable from more than one parent: node objects referencing each other however you named the reference, or a plain adjacency dict like {'A': ['B', 'C']}.
    • 
      
  • Arrays and heaps — any plain list/tuple of numbers or strings, with a toggle to also view it as the implicit binary tree a heap represents.
    • 
      
  • Mappings and sets — a plain dict or set/frozenset of primitive values, shown as key→value chips or a value cluster.
    • 
      
  • Queues — a collections.deque of primitives specifically (an actual type distinction, not a naming guess), shown with front/rear labels. A plain list used as a stack or queue just renders as an array — the push/pop/enqueue/dequeue behavior is fully visible in how it grows and shrinks.
    • 
    

    
A node's on-screen label is built the same shape-first way: whichever of its own attributes hold plain values (numbers, strings, booleans) get shown; attributes holding other objects become the structural connections instead. None-valued attributes are left out of the label, since on a node object that almost always means "link not set" rather than meaningful data.

  

  

    
Limits of a fully generic approach

    
Detecting shape instead of names removes every constraint on what you can call things, but it does trade away a few things a naming convention could otherwise tell it for free:

    
    
      
  • When several structures are live at once, the tool shows whichever one is largest and most actively being mutated. A big, unrelated lookup table can occasionally win a tie against a small structure that hasn't grown yet — it'll switch over once the real one gets bigger.
    • 
      
  • For a doubly-linked list or a genuinely circular structure, there's no way to know which node you consider "the start" without a naming hint — the tool picks whichever end/point it happens to track, which may not always match your mental picture of head-to-tail.
    • 
      
  • A small graph whose edges happen to form a single loop (a "ring") is mathematically identical to a circular linked list from the shape alone, so it may render as a circular chain rather than a general graph layout.
    • 
    

    
None of these produce wrong data — the nodes, values, and connections shown are always exactly what your code built. They can occasionally affect which structure gets picked or which end a chain is drawn from.

  

  

    
Common uses

    
    
      
  • Debugging your own tree, linked list, graph, or heap insert/delete/search implementations for a data structures course or coding interview prep
    • 
      
  • Visualizing depth-first and breadth-first traversal order on a real tree or graph
    • 
      
  • Watching a linked list get reversed, or a heap get sifted up/down, node by node
    • 
      
  • Understanding how recursive functions build up and unwind a call stack while operating on a structure
    • 
      
  • Teaching data structure concepts with a live, real-code demonstration instead of a static diagram
